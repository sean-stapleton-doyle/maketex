# Designing a Modern Replacement for latexmk: A Technical Research Report and Design Document

## TL;DR
- **latexmk works because it treats LaTeX as a fixed-point computation: it runs the engine repeatedly until the generated files (chiefly the `.aux`, plus `.toc`, `.bbl`, `.bcf`, index/glossary files) stop changing, deciding "changed" by MD5 checksum rather than timestamp, and capping the loop at `$max_repeat = 5` runs. A replacement must reproduce this checksum-driven fixed-point loop and latexmk's dependency discovery from `.fls`, `.log`, and `.aux` files — anything less will silently produce documents with stale cross-references.**
- **The dependency graph is the core data model: file nodes (source `.tex/.sty/.cls/.bib/.png/.pdf/fonts`, generated `.aux/.toc/.bbl/.glstex/.ind`) and rule nodes (latex engine, bibtex/biber, makeindex/xindy, makeglossaries/bib2gls, custom tools). Edges come from parsing the `-recorder` `.fls` file (authoritative read/write list) supplemented by `.log` and `.aux` parsing. The latex rule is special: it is simultaneously the producer and consumer of many generated files, which is exactly why iteration is required.**
- **For a C++ implementation, the recommended architecture is: (1) a persistent file-state database keyed on (mtime, size, content-hash); (2) a rule engine doing topological scheduling with a bounded fixed-point outer loop and divergence detection; (3) parallelism limited to genuinely independent rules (multiple independent bibliographies/indexes); (4) a watch mode using OS file-notification APIs; (5) structured `.log`/`.blg`/`.ilg` parsing to surface errors; and (6) declarative extension points for shell-escape tools (pythontex, minted, tikz externalize). Tectonic's auto-fetching engine model is worth adopting as an optional backend but changes the dependency story.**

## Key Findings

1. **Multiple passes exist because LaTeX is single-pass over the source but needs information that is only known after a full pass.** Forward references (`\ref`, `\pageref`, `\cite`, page numbers in the table of contents) are written to the `.aux` file (and `.toc`/`.lof`/`.lot`) on one pass and read on the next. A typical bibliography build is `pdflatex → bibtex → pdflatex → pdflatex`; with biblatex/biber it is `pdflatex → biber → pdflatex → pdflatex`. As a brute-force guarantee, the Makefile generated by `sphinx-build -b latex` runs pdflatex **5 times** (per readthedocs.org issue #749, citing Sphinx's own source).

2. **latexmk's rerun decision is checksum-based, not timestamp-based.** The source comment is explicit: "The correct criterion for whether a source is out-of-date is therefore NOT that its modification time is later than the destination file, but whether the contents of the source file have changed since the last successful run … we instead use the md5 signature of the files." It stores a `(time, size, md5)` triple per file; if time and size are unchanged it skips recomputing the MD5 as an optimization. The default rerun cap is `$max_repeat = 5`.

3. **The `.fls` file (produced by `-recorder`) is the authoritative dependency source.** It is a simple line-based text file with `PWD`, `INPUT <path>`, and `OUTPUT <path>` records listing every file the engine opened for reading or writing, with full paths. This is far more reliable than parsing the `.log` file, though latexmk uses all three of `.fls`, `.log`, and `.aux`.

4. **Each auxiliary tool has a well-defined I/O contract** that maps cleanly onto graph edges (detailed in the Details section): bibtex (`.aux`+`.bib`+`.bst`→`.bbl`+`.blg`), biber (`.bcf`→`.bbl`+`.blg`), makeindex (`.idx`→`.ind`+`.ilg`; nomenclature `.nlo`→`.nls`), xindy (same role as makeindex), makeglossaries (`.glo`/`.acn`→`.gls`/`.acr`), and bib2gls (`.aux`+`.bib`→`.glstex`).

5. **Tectonic changes the model**: it is a self-contained XeTeX-derived engine that auto-fetches packages from a bundle on demand and runs its own internal multi-pass loop. Per the project's own description, "Tectonic has sophisticated logic and automatically loops TeX and BibTeX as needed, and only as much as needed. In its default mode it doesn't write TeX's intermediate files and always produces a fully-processed document," and "If you start using a new LaTeX package, Tectonic just pulls down the files it needs and continues processing" (default cache `$HOME/.cache/Tectonic`, overridable via `$TECTONIC_CACHE_DIR` as of v0.9.0). It thus needs no external driver for the core latex/biber cycle — but it externalizes the dependency-resolution question (network/cache) that latexmk never had.

6. **The main user pain points** are: log noise burying real errors, slow builds on large/TikZ-heavy documents, fragile handling of preprocessors (latexmk forces the latex rule to be primary, making knitr/pweave awkward), and Perl/config complexity. A replacement's biggest opportunities are clean error surfacing, parallelism, and first-class preprocessor/extension support.

## Details

### 1. The LaTeX build workflow and why passes exist

LaTeX processes source linearly in a single pass, but a document needs information that only exists after the whole document has been seen — section/figure/table numbers, page numbers, citation labels. LaTeX's solution is to write this information to auxiliary files during a run and read it back on the next run:

- On pass 1, `\label`/`\caption`/`\section` write entries to the `.aux` (and `.toc`, `.lof`, `.lot`); `\cite` keys are written to the `.aux`. At this point `\ref`/`\cite` in the output show `??` or `[?]`.
- On pass 2, LaTeX reads the `.aux` from pass 1 so `\ref` resolves; but if resolving references shifted page numbers, the `.toc`/page references may now be stale, so LaTeX emits `LaTeX Warning: Label(s) may have changed. Rerun to get cross-references right.`
- Passes continue until no generated file that is re-read changes. Most documents converge in 2–3 passes; some document classes (latexmk's source cites JHEP.cls) need 4; latexmk allows 5.

**The bibliography sub-cycle.** With classic BibTeX: pass 1 writes `\citation` and `\bibstyle`/`\bibdata` records to the `.aux`; `bibtex <job>` reads the `.aux` + the `.bib` database + the `.bst` style and writes a `.bbl` (the formatted bibliography) and `.blg` (log); pass 2 `\input`s the `.bbl`, defining the bibliography but in-text `\cite`s still show `[?]`; pass 3 resolves the `\cite` labels. With biblatex+biber: LaTeX writes a `.bcf` (an XML "biblatex control file"); `biber <job>` reads the `.bcf`, fetches and sorts data from the `.bib` files, and writes the `.bbl` + `.blg`; biber emits `Package biblatex Warning: Please (re)run Biber on the file … and rerun LaTeX afterwards.` to signal the driver.

**The fixed-point concept.** A LaTeX build is done when running the engine produces no change in any file that the engine itself re-reads on a subsequent run — i.e. the generated-and-reread set (`.aux`, `.toc`, `.lof`, `.lot`, `.out`, `.bbl`, `.ind`, `.gls`, …) has reached a fixed point. latexmk detects this by checksumming those files before and after each run and stopping when nothing changed (or when `$max_repeat` is hit). Divergence (a file that oscillates or whose datestamp changes every run) is the pathological case the cap exists to break.

### 2. Auxiliary files and what triggers reruns

Key auxiliary file roles:

| Extension | Producer | Consumer | Role |
|---|---|---|---|
| `.aux` | latex | latex, bibtex, bib2gls | cross-refs, citation keys, label table |
| `.toc`/`.lof`/`.lot` | latex | latex | table of contents / list of figures / tables |
| `.out` | hyperref (latex) | latex | PDF bookmarks/outlines |
| `.bbl` | bibtex/biber | latex | formatted bibliography |
| `.blg` | bibtex/biber | (log) | bibliography processing log |
| `.bcf` | latex (biblatex) | biber | biblatex XML control file |
| `.run.xml` | latex (biblatex) | (tools) | biblatex run metadata |
| `.idx` | latex (makeidx) | makeindex/xindy | raw index entries |
| `.ind`/`.ilg` | makeindex/xindy | latex / (log) | sorted index / index log |
| `.nlo`/`.nls`/`.nlg` | latex / makeindex | makeindex / latex | nomenclature in/out/log |
| `.glo`/`.gls`/`.glg` | latex / makeglossaries | makeglossaries / latex | glossary in/out/log |
| `.acn`/`.acr`/`.alg` | latex / makeglossaries | makeglossaries / latex | acronym in/out/log |
| `.glstex` | bib2gls | latex | glossary definitions (bib2gls) |
| `.fls` | latex (`-recorder`) | the build tool | read/write trace |
| `.log` | latex | the build tool | run transcript |
| `.fdb_latexmk` | latexmk | latexmk | file-state database |

**Rerun triggers** are detected two ways. Primarily, latexmk compares the MD5 of generated-and-reread files across the run. Secondarily it scans the `.log` for warning strings. latexmk maintains parse-result state variables including `$reference_changed`, `$mult_defined`, `$bad_reference`, `$bad_citation`. The recognized warnings include `LaTeX Warning: Label(s) may have changed. Rerun to get cross-references right.`, `LaTeX Warning: There were undefined references.`, `Citation '…' … undefined`, the rerunfilecheck package's `Rerun to get outlines right`, and biblatex's `Please (re)run Biber …`. latexmk's `@generated_exts` default array (`aux`, `bcf`, `fls`, `idx`, `ind`, `lof`, `lot`, `out`, `run.xml`, `toc`, `blg`, `ilg`, `log`, `xdv`) is used both for cleanup and to decide whether a rerun is needed after an errored run.

**`\input` vs `\include`.** Both bring in source text; `\include` additionally writes a separate `.aux` per included file and works with `\includeonly`. For dependency tracking the distinction barely matters because the `.fls` records every file actually opened — the build tool does not need to parse `\input`/`\include` itself if the recorder is on. As a cautionary tale for a reimplementation, the latexmk CHANGES file records a long-standing bug fixed only in v4.11: "Corrects a long-standing bug that when the main file uses bibtex, and uses `\include` for subdocuments, changes in bibliography citations did not always trigger a rerun of bibtex."

### 3. The `.fls` file format

Running `pdflatex -recorder <job>` (also xelatex/lualatex) produces `<job>.fls`. Its format is line-oriented; a real example:

```
PWD /home/yuri/texmf/knoeien
INPUT /home/yuri/.texlive2007/texmf-var/web2c/pdftex/pdflatex.fmt
INPUT centaurtestje.tex
OUTPUT centaurtestje.log
INPUT /usr/local/texlive/2007/texmf-dist/tex/latex/base/article.cls
INPUT /usr/local/texlive/2007/texmf-dist/tex/latex/base/size10.clo
INPUT centaurtestje.aux
OUTPUT centaurtestje.aux
OUTPUT centaurtestje.pdf
INPUT /usr/local/texlive/2007/texmf-var/fonts/map/pdftex/updmap/pdftex.map
```

Semantics: one `PWD` line giving the working directory, then any number of `INPUT <path>` and `OUTPUT <path>` lines (paths may be absolute or relative to `PWD`). The same file can appear as both INPUT and OUTPUT (the `.aux` is the canonical case — written then re-read). A file that is read *after* it was written in the same run is in a dependency loop, which is precisely the signal that another pass may be needed. The `.fls` is always UTF-8. Notable quirks: MiKTeX historically wrote `.fls` to the output directory rather than the aux directory; engines have had bugs with relative `-output-directory` paths; MiKTeX writes absolute paths and is inconsistent about `/` vs `\` separators.

### 4. latexmk internals (the design to learn from)

**File-state database (`fdb_latexmk`).** latexmk persists a database file (`$fdb_ext = 'fdb_latexmk'`, version `$fdb_ver = 4`). Per file it stores a `[time, size, md5]` triple (a size of `-1` flags a non-existent file). Per rule it writes a header line of the literal form:

```
["rule"] run_time "source" "dest" "base" check_time
```

followed by the list of source files with their `(time, size, md5)` data. On startup latexmk reads this DB; if absent, the first run falls back to timestamp-based out-of-dateness (with knowledge of which files are engine-generated and re-read).

**The rerun algorithm**, paraphrased from the source's numbered comment block:
1. For each rule (latex/pdflatex, each custom dependency) keep a DB of source-file state used by the last run.
2. On startup, read the DB if it exists; else use timestamps.
3. Run the rule.
4. After the run, recompute state for all source files (both files written by the run that are in a dependency loop, and files the user may have edited mid-run).
5. For latex/pdflatex, also check and rebuild out-of-date custom dependencies.
6. If any source file changed, redo the run from step 1.
7. Bound the number of reruns (`$max_repeat = 5`) to avoid infinite loops.
8. After completion, update the DB.

**Checksum-ignore patterns.** Because some generated files embed a changing datestamp (e.g. an EPS `%%CreationDate:` line) that would cause endless reruns, latexmk lets you register a regex per extension (`$hash_calc_ignore_pattern{'eps'} = '^%%CreationDate: ';`) telling it which lines to exclude from the MD5. A replacement needs the equivalent.

**Configuration (`.latexmkrc`).** latexmk is configured by Perl rc files (system, user `~/.latexmkrc`, and per-directory `.latexmkrc`/`latexmkrc`), and by `-e 'perl code'` on the command line. Configurable items include the command strings for each engine (`$pdflatex`, `$xelatex`, `$lualatex`, `$biber`, `$bibtex`, `$makeindex`), silent-mode switches, `$bibtex_use` (0/1/1.5/2 controlling whether/when bibtex runs and whether `.bbl` is "precious"), `$max_repeat`, `$out_dir`/`$aux_dir`/`$out2_dir`, `@default_files`, `@generated_exts`, `$clean_ext`, and **custom dependencies** (`add_cus_dep`) keyed by from-extension/to-extension with a Perl subroutine to run the tool. The use of a full Perl interpreter for config is powerful but is a portability and security liability for a C++ reimplementation.

**Continuous/preview mode (`-pvc`).** latexmk watches all source files and reruns the whole build when any changes, refreshing a previewer. It also supports an `out2dir` so a PDF viewer only sees the final converged PDF rather than every intermediate pass — a UX detail worth copying.

**Known pain points.** (a) Error visibility: LaTeX errors reference internal macros and are buried in log noise; users routinely fall back to reading `.log` manually. (b) Preprocessors: latexmk treats the latex rule as the special primary rule run before all others, which makes knitr/lhs2TeX/Pweave/pythontex preprocessing awkward (DiCy was built specifically to fix this — "its build procedure does not need to start with LaTeX and can start with preprocessors such as knitr"). (c) Speed on large/TikZ-heavy documents. (d) Custom dependencies don't have the same priority as built-in rules.

### 5. Engine differences

- **pdflatex** (pdfTeX engine): reads/writes PDF directly, natively handles PDF/PNG/JPG/JBIG2 images, cannot include EPS without `epstopdf`. Fastest of the three.
- **xelatex** (XeTeX engine): native Unicode + system OpenType/TrueType fonts via fontspec. Crucially it produces an intermediate **`.xdv`** (extended DVI), then converts to PDF via **`xdvipdfmx`** — a two-stage pipeline, so the dependency graph has an extra node. latexmk invokes it with the `-no-pdf` default switch (`$xelatex_default_switches = '-no-pdf'`) to get the `.xdv`. Slightly slower; more limited microtype support.
- **lualatex** (LuaTeX engine): Lua embedded in the engine; direct PDF output; can run Lua during compilation (which can read/write arbitrary files, complicating dependency tracking). Had a known TeXLive 2016/2017 bug where files were created/read/deleted within a run, confusing latexmk.
- **tectonic**: self-contained XeTeX/TeXLive-derived engine that **auto-downloads needed packages from a web bundle on demand** (caching to `~/.cache/Tectonic`), and runs its own internal multi-pass loop, so a single `tectonic` invocation can produce a finished PDF without an external driver. Trade-off: dependency resolution becomes a network/cache concern, and the `-X` "v2" interface adds project/build features.

All engines accept `-recorder` (→`.fls`), `-interaction=batchmode/nonstopmode`, `-output-directory`, `-synctex=1` (editor sync; produces `.synctex.gz`), `-shell-escape` (enables `\write18`), and `-halt-on-error`.

### 6. Alternative build systems / prior art

- **latexmk** (Perl, John Collins): the de-facto standard; reliable fixed-point algorithm, `.fls`/`.log`/`.aux` dependency discovery, continuous preview. Used by Overleaf and most editor integrations under the hood.
- **arara** (Java, Island of TeX): rule-based, directive-driven — the user annotates the source with `% arara: pdflatex` comments specifying exactly which tools run, in what order, how many times. Per the arara manual: "That is the major difference of arara when compared to other tools: it is not an automatic process and the tool does not employ any guesswork on its own. You are in control of your documents; arara will not do anything unless you teach it how to do a task and explicitly tell it to execute the task." Reproducible and explicit but manual; it does not auto-detect reruns. Requires a JVM.
- **rubber** (Python): wrapper that compiles "enough times to resolve references," running bibtex/makeindex/metapost as needed; users report `--clean` missing some files and weak LuaTeX support.
- **DiCy** (JavaScript, yitzchak): log-parsing auto-rule-selection like latexmk but with a larger built-in rule set and, importantly, the ability to start with preprocessors (knitr) and to filter/display log messages by severity (Asymptote/Biber/BibTeX/LaTeX/makeindex/xindy). Good model for error surfacing and preprocessor support.
- **l3build** (Lua, LaTeX Project): aimed at *package* development and regression testing, not document builds — compares run logs against known-good `.tlg` reference files across pdftex/xetex/luatex engines. Relevant for its cross-engine test harness design, not as a document driver.
- **tectonic's built-in loop** and **latexrun** (a precompiled-preamble approach reported as fast in one comparison): worth studying for speed.
- **Make/CMake/SCons-based** approaches: full generality but the user must encode the fixed-point loop by hand; brittle.

## Recommendations

A staged plan for a C++ implementation, with the thresholds that should change the approach.

**Stage 1 — Correct single-document builds (MVP).**
1. **Data model.** Build a bipartite directed graph of **File nodes** and **Rule nodes**. File node: canonical absolute path, role (source/generated/output), and cached `(mtime, size, content-hash, ignore-regex)`. Rule node: command template, input-extension/output-extension contract, and the actual input/output file sets discovered at runtime. Edges: File→Rule (rule consumes file) and Rule→File (rule produces file). Model the latex rule explicitly as both consumer and producer of the generated-and-reread set; that self-loop is what forces iteration.
2. **Rerun detection.** Implement the minimal correct algorithm: hash every generated-and-reread file before the run; run the engine; rehash; if any changed, schedule another pass. Use the `(mtime, size)` fast path to skip hash recomputation. Use a strong, fast non-cryptographic hash (xxHash/BLAKE3) rather than MD5 — there is no security requirement, only change-detection. Support per-extension ignore-line regexes (the `%%CreationDate:` problem).
3. **Dependency discovery.** Always invoke engines with `-recorder` and parse the `.fls` as the authoritative read/write list; supplement with `.log` (for not-found files and rerun warnings) and `.aux` (for `\citation`/`\bibdata`/`\@input`). Normalize paths against the `.fls` `PWD` line and handle MiKTeX's absolute-path/separator quirks.
4. **Fixed-point loop.** Bound the outer loop with a configurable `max_passes` (default 5, matching latexmk). Detect **convergence** (no generated-and-reread file changed) vs **divergence** (a file's hash oscillates across ≥2 passes, or the changed-set is non-decreasing after N passes) and emit a clear diagnostic naming the oscillating file rather than silently hitting the cap.
5. **Tool rules.** Ship built-in rules for bibtex, biber (triggered by `.bcf` presence), makeindex (`.idx`→`.ind` and nomenclature `.nlo`→`.nls -s nomencl.ist`), xindy, makeglossaries/makeglossaries-lite, and bib2gls (`.aux`→`.glstex`, needs the `--group` nuance). Trigger each by the presence/change of its input file, and schedule it before the next latex pass.

**Stage 2 — Usability.**
6. **Error surfacing.** Parse `.log`, `.blg`, `.ilg`, biber/bib2gls logs into structured diagnostics (severity, file, line, message) and present errors and "bad" warnings first, collapsing routine noise — the single biggest user complaint and the clearest differentiator. Treat configurable warning classes (e.g. undefined references after the final pass) as build failures, like latexmk's `$bad_warning_is_error`.
7. **Watch/incremental mode.** Implement a continuous mode on native file-notification APIs (inotify on Linux, FSEvents/kqueue on macOS, ReadDirectoryChangesW on Windows) rather than polling; debounce events; rebuild only the affected rules using the persisted state DB; and expose an "only update the final output once converged" option so PDF viewers don't flicker through intermediate passes.
8. **Configuration model.** Use a declarative config (TOML/YAML) for the 95% case — engine selection, tool commands, directories, `max_passes`, clean/precious extension lists, ignore-line patterns — and a sandboxed scripting hook (Lua, à la l3build/tectonic, **not** an embedded full system shell) for custom dependencies and exotic tools. This deliberately avoids latexmk's Perl-eval portability/security problem.

**Stage 3 — Performance and extensibility.**
9. **Parallelism.** The latex passes themselves are strictly sequential (each depends on the previous). The real parallelism is across **independent rules**: multiple independent bibliographies, multiple `\GlsXtrLoadResources`/indexes, and figure/externalize jobs can run concurrently; bibtex/biber for one document and an unrelated index can overlap. Schedule by topological level and run independent nodes on a thread pool. Do **not** try to overlap a bibtex run with the latex pass that consumes its output. TikZ externalization (`mode=list and make`, which emits a `.dep`/makefile of per-figure dependencies) is embarrassingly parallel and is the highest-value parallel target.
10. **Extension points for shell-escape tools.** Provide first-class, declarative rules for pythontex (`.pytxcode`→`pythontex`→re-run latex), minted (needs `-shell-escape` and `pygmentize`; emits temp files that must not trigger false reruns), and tikz externalize. Note the real-world constraint that pythontex is *not* compatible with TikZ externalization, and that minted creates/deletes temp files within a run (the same class of problem that broke latexmk with lualatex/minted) — the state DB must tolerate files that appear and disappear mid-run.
11. **Preprocessor-first builds.** Unlike latexmk, do **not** hard-code latex as the mandatory first rule. Allow the graph to start at knitr/pweave/lhs2TeX/pandoc producing the `.tex`, then feed the normal loop — this is DiCy's key advantage and resolves a major latexmk limitation.
12. **Optional tectonic backend.** Support tectonic as an alternative engine that internalizes the multi-pass loop and package fetching; when used, your driver's job shrinks to preprocessing, glossary/index tools tectonic doesn't run, watch mode, and error surfacing. Cache management (the bundle download) becomes a first-class concern.

**Benchmarks that should change the design.** If profiling shows hashing dominates on large documents, widen the `(mtime, size)` fast path and memory-map files. If divergence false-positives appear, expand the ignore-line regex library. If users predominantly use one engine + biber + no exotic tools, ship that as a zero-config default and defer the scripting hook.

## Caveats

- **Source-version specificity.** The internal details (`$max_repeat = 5`, `$fdb_ext`/`$fdb_ver = 4`, the `(time, size, md5)` triple, the `["rule"] run_time "source" "dest" "base" check_time` line format, `@generated_exts`) were read from latexmk.pl version 4.88 (dated 9 March 2026). These are implementation details that have changed across versions (the CHANGES file shows the database format and rerun logic evolving) and may change again; treat them as a reference implementation, not a spec.
- **Regex literals not fully captured.** The subagent retrieved latexmk's parse-result state variables and the warning *strings* verbatim, but the exact Perl regular-expression literals inside `sub parse_log` were beyond the truncation point of the fetched source. A reimplementer should grep the live source (e.g. the GitHub mirror at `github.com/latexjs/latexmk`) for the precise patterns before hard-coding them.
- **`.fls` is necessary but not sufficient.** The recorder lists files opened by the engine, but tools invoked via `\write18`/shell-escape (minted, pythontex, gnuplot, tikz externalize sub-runs) open files the parent engine never sees; those dependencies must be captured by tool-specific rules, not the `.fls` alone.
- **Some cited sources are secondary or commercial.** Workflow descriptions drew on vendor/educational pages (Overleaf, FormaTeX, SysTutorials) which are reliable for the well-established mechanics described but are not primary specifications; engine and tool behavior was cross-checked against man pages and official package documentation (TikZ/PGF manual, bib2gls/dickimaw, biber manual).
- **No formal `.fls`/`.aux`/`.bcf` grammar exists.** These formats are defined operationally by the TeX engines and packages that emit them; a robust parser should be permissive and tolerate the documented MiKTeX/engine path-separator and relative-path quirks.
- **Performance claims about alternatives** (e.g. latexrun being "fastest," tectonic's speed) come from individual blog benchmarks on specific documents and should be re-benchmarked on representative workloads before being used to justify architecture decisions.
